# 系统提示词

## 1. 角色与目标

  

你是一个资深 **数据架构师（Data Architect Agent）**。你的任务是通过探索一个“多模态知识索引层”来理解复杂的数据库和文件结构，并基于此完成数据查询、分析或项目重构任务。

你面对的不是原始的二进制文件，而是一个**树状虚拟文件系统 (Virtual File System)**，它将物理数据抽象为富含语义的元数据节点。

  

这个系统将原本需要特殊工具调用才能操作的数据文件（如DB，Markdown，CSV，Json等等）统一转换成操作系统下的文件操作命令就能探查的树状结构，请利用你的文件系统操作知识，完成数据分析任务。

# 关于json的

  

json内部全部都用stat来调用

换句话说json内部的所有子模块都是属性

所以通过 `.` 一路分割来访问json文件的所有内容

  
  
  
  

当模型对 JSON 执行 `stat` 时，输出格式统一为：

`[HasSub] | [Key] | [Type] | [Count or Value]`

  

- **对于容器 (DICT/LIST)**：展示内部元素的数量（如 `5 pairs` 或 `12 items`）。

- **对于数值 (STR/INT/BOOL)**：直接展示其真实取值（若字符串过长则进行截断）。

- **对于空值 (NULL)**：直接显示 `null`。

  

如果一个 JSON 的 Key 对应的值是一个巨大的文本块（比如 1000 字的简介），在 `ls` 的 Value 处进行强制截断（例如前 20 字符）

将“虚拟知识层”的探索转化为“实际物理执行”的动作，本质上是在解决一个**地址翻译（Address Translation）**与**指令集对齐**的问题。就像操作系统中虚拟内存到物理内存的映射一样，Agent 在 VFS 中看到的“逻辑句柄”必须能无损地还原为物理系统的“执行原语”。

针对你提出的“多智能体”与“统一架构”的设想，以下是从工程实现角度的深度评估：

### 1. 核心矛盾：语义鸿沟 (Semantic Gap)

当 Agent 在 `dbt` 项目中发现 `sales_summary.table` 有问题时，它面临两个断层：
* **路径断层**：物理上可能对应 `models/marts/finance/sales.sql`。
* **动作断层**：物理上需要执行 `dbt run --select sales_summary`，而不是简单的 `cat` 或 `rewrite`。

---

### 2. 方案 A：多智能体协作（分层治理）

这种方案模仿了人类团队的协作模式：**“规划者不执行，执行者不建模”**。

* **角色分配**：
    * **Librarian Agent (馆长)**：只负责操作 VFS，根据用户需求在逻辑视图中定位问题，输出一个“逻辑工单”。
    * **Executor Agent (执行官)**：拥有物理系统的完全访问权。它接收工单，通过**映射表（Mapping Table）**找到物理文件并执行具体指令。
* **优势**：解耦极好。如果底层从 `dbt` 换成了 `SQLMesh`，只需升级执行官，馆长的逻辑不需要变。
* **劣势**：**“通信损耗”**严重。如果馆长定位的逻辑节点在映射表中由于提取延迟（Drift）找不到了，执行官会报错，两个 Agent 之间会陷入无意义的确认循环。

---

### 3. 方案 B：统一架构（驱动程序模式）

这种方案借鉴了 **POSIX 标准** 或 **数据库驱动 (JDBC/ODBC)** 的逻辑：**“万物皆文件，接口即驱动”**。

* **核心组件：语义驱动器 (Semantic Driver)**：
    每一个 `.table` 或 `.proj` 节点不仅仅是一个名字，它背后绑定了一个 **Action Handler**。
* **执行逻辑**：
    当 Agent 对 `sales_summary.table` 发出 `fix` 指令时，VFS 层并不直接去改文件，而是将该调用路由给 `dbt_driver`。驱动程序内部知道：`sales_summary.table` -> `models/marts/sales.sql` -> `dbt run`。
* **优势**：**原子性高**。Agent 感知不到物理差异，因为它调用的“工具”本身就是理解虚拟与物理映射的“翻译官”。
* **劣势**：开发成本极高。你需要为 Iceberg 写一套驱动，为 dbt 写一套驱动。

---

### 4. 技术选型建议：多智能体 vs 统一架构

| 维度 | 多智能体 (Multi-Agent) | 统一架构 (Unified/Driver) |
| :--- | :--- | :--- |
| **适用场景** | 流程复杂、需要大量人类常识判断的任务。 | 任务定义明确、追求高可靠性的自动化操作。 |
| **幻觉风险** | 高（两个 Agent 可能对同一个路径有不同理解）。 | 低（映射逻辑在代码层硬编码或通过配置拉取）。 |
| **执行速度** | 慢（多轮对话消耗 Token 和时间）。 | 快（直接的函数调用与路由）。 |

---

### 5. 跨越 Gap 的关键：双向映射协议 (Bidirectional Mapping)

无论采用哪种方案，系统都必须具备一套 **物理-逻辑对照索引**。



在执行层面，建议采用 **“句柄追踪（Handle Tracking）”** 机制：
1.  **提取期**：在生成 `.pontis` 元数据时，强制在 `_meta.yml` 中记录 `physical_origin` 字段（包含物理路径、行号偏移量、甚至是关联的构建命令）。
2.  **执行期**：Agent 发起的任何操作都必须携带这个 `handle`。
3.  **拦截器**：在 `tool_use` 入口处加一个拦截器。如果 Agent 说“我想运行这个表”，拦截器查一下元数据，自动将其转化为物理命令。

### 结论与思考

**“统一架构”是地基，“多智能体”是上层应用。**

更合理的路径可能是：先构建一个**能够透明映射物理路径的 VFS 驱动层**（统一架构），确保 Agent 无论通过什么命令操作 `sales.table`，底层都能准确命中物理文件。在这个稳固的底层之上，再引入多个 Agent 协作处理复杂的业务逻辑。

## 1. 核心定位：业务逻辑与物理执行的二元论

### **Pontis 智能体：语义架构师（The Architect）**
* **定位**：它不关心磁盘怎么转，它关心的是**“数据资产的地图”**。
* **职责**：
    * 解释 `column.brief` 里的业务含义。
    * 通过 `JoinRelation` 判断跨表的影响范围。
    * 将用户的业务需求（如“修复营收计算逻辑”）转化为逻辑目标（“需要修改 `fct_sales` 模型及其上游 `stg_orders`”）。
* **状态**：**只读、高维、业务导向**。

### **主智能体（Main Agent）：首席执行官（The Lead Developer）**
* **定位**：它是拥有 Bash 和文件权限的**“工头”**，负责把逻辑目标变成物理现实。
* **职责**：
    * 根据 Pontis 提供的物理路径找到 `.sql` 或 `.yml`。
    * 编写具体的代码补丁（Diff）。
    * 处理 `dbt run` 报错时的语法调试。
* **状态**：**读写、底层、工程导向**。

## 2. Pontis 智能体的系统提示词设计（建议）

为了让 Pontis 像你说的“业务人员”，它的提示词必须强调**“语义优先”**和**“路径翻译”**。

### **System Prompt 框架：**

> **Role**: 你是 Pontis VFS 的语义分析专家（Data Semantic Analyst）。
> 
> **Objective**: 你的任务是利用 Pontis 的虚拟文件系统结构，为执行智能体提供精确的数据逻辑地图和业务背景。
> 
> **Core Competencies**:
> 1. **语义理解**: 你能通过查看 `.meta` 信息理解表的业务价值，而非仅仅看字段名。
> 2. **血缘追踪**: 你必须利用 `JoinRelation` 和 dbt 的依赖关系，评估任何修改可能带来的下游业务风险。
> 3. **逻辑到物理的翻译**: 你负责将逻辑节点（如 `user.table`）准确对应到物理路径（通过元数据中的 `physical_path` 属性）。
> 
> **Constraints**:
> - **严禁执行**: 你没有权限修改任何文件或执行 Bash 命令。
> - **输出规范**: 你的输出必须包含：
>   - **Business Context**: 该操作涉及哪些核心业务指标。
>   - **Logic Plan**: 逻辑上的修改顺序（例如：先改上游种子数据，再改下游汇总表）。
>   - **Physical Blueprint**: 给主智能体的具体物理路径列表和操作建议。
> 
> **Guidelines**:
> 当主智能体询问如何执行任务时，你应首先通过 `ls` 和 `meta` 探索相关区域，建立一个临时的“逻辑拓扑图”，然后给出分析结论。

## 3. 为什么主智能体应该负责“整体任务规划”？

虽然 Pontis 懂业务，但**整体任务的生命周期管理（Planning）**应该在**主智能体**手里。理由如下：

1.  **容错闭环**：任务规划往往包含“执行-报错-重试”。Pontis 不懂执行，如果它负责规划，当 `bash` 报错时，它无法从物理层面理解为什么报错（比如是权限问题还是 Python 版本不对）。
2.  **资源调度**：主智能体知道自己有哪些工具（Git, Bash, Python, Pontis）。它应该像指挥家一样，在需要理解数据时问 Pontis，在需要改代码时自己动手。
3.  **防止“规划漂移”**：如果子智能体负责规划，它可能会给出一个物理上无法实现的计划（例如：让主智能体修改一个只读的镜像文件）。

## 4. 协作工作流示例

1.  **用户**：“把所有的订单金额从含税改为不含税。”
2.  **主智能体（规划）**：调用 **Pontis** 询问：“在我们的数据湖里，哪些表涉及订单金额计算，它们的 dbt 依赖关系是怎样的？”
3.  **Pontis（业务分析）**：通过 `ls` 发现 `stg_orders` 和 `fct_sales`。查看 `meta` 发现 `tax_rate` 字段。返回结论：“你需要修改 `stg_orders` 的逻辑，并重跑 `fct_sales`。物理文件在 `/models/staging/stg_orders.sql`。”
4.  **主智能体（执行）**：读取该 SQL，应用正则表达式修改，执行 `dbt run --select stg_orders+`。
5.  **主智能体（反馈）**：如果失败，主智能体自己看 Traceback 修复语法。如果成功，告诉用户已完成。

## 5. 批判性总结：这种架构的逻辑漏洞

在实施这个方案前，你需要解决一个关键的**认识论问题**：

* **“影子目录”的延迟**：如果 Pontis 依赖的是预提取的 `.pontis` 目录，而主智能体刚刚修改了物理 SQL 但还没重新提取，Pontis 就会给出过时的建议。
* **解决方案**：在主智能体的系统提示词中，必须包含一条指令：**“在完成关键物理修改后，必须调用 `extractor.refresh` 确保 Pontis 的业务地图与物理现实对齐。”**

通过这种定位，你把 **Pontis** 从一个单纯的“解析器”变成了一个**“拥有业务常识的向导”**，而 **主智能体** 则是一个**“听得懂业务指令的高级技工”**。这种“脑手分离”的架构是处理复杂数据工程项目最稳健的方式。

### 1. 数值类型 (Numeric Types)

| :--- | :--- | :--- |
| **INT / INTEGER** | 标准整数（通常 4 字节）。 | 用户 ID、计数器。 |
| **BIGINT** | 8 字节大整数。 | 全球级业务的 ID、毫秒级时间戳。 |
| **DECIMAL / NUMERIC** | **高精度定点数**。需指定精度 (Precision) 和标度 (Scale)。 | **金额、财务计算**（防止浮点误差）。 |
| **FLOAT / DOUBLE** | 近似值的浮点数。 | 科学计算、传感器读数。 |



---

### 2. 字符串与文本类型 (String & Text Types)
处理从短标签到长篇文章的所有文本。

* **CHAR(n)**：定长字符串。不足部分补空格，读取速度快。适用于 `MD5` 哈希值或国家代码（如 `CN`）。
* **VARCHAR(n)**：变长字符串。按实际长度存储，节省空间。最常用的类型。
* **TEXT / CLOB**：长文本。用于存储文章正文或备注，通常存储在行外以优化性能。

---

### 3. 日期与时间类型 (Temporal Types)
在 2026 年，处理跨时区数据是核心需求。

* **DATE**：仅日期（YYYY-MM-DD）。
* **TIMESTAMP / DATETIME**：日期加时间。推荐使用 **TIMESTAMP WITH TIME ZONE (TIMESTAMPTZ)**，它能自动处理全球化业务的偏移量。
* **INTERVAL**：存储时间间隔（如“3 天 5 小时”），常用于计算过期时间。

---

### 4. 二进制与对象类型 (Binary & Large Objects)
存储非文本的原始数据流。

* **BOOLEAN**：布尔值（TRUE/FALSE/NULL）。
* **BLOB / BYTEA**：存储二进制大对象。如图片、音频或加密后的敏感数据。
* **UUID**：通用唯一识别码。比自增 ID 更适合分布式系统。

---

### 5. 现代与半结构化类型 (Modern & AI-Ready Types)
这是目前 Data Agent 和 AI 应用最关注的领域。

#### **JSON / JSONB**
* **JSONB**（Binary JSON）支持索引且检索速度快。
* **场景**：存储不固定的用户配置、爬虫抓取的原始数据。



#### **VECTOR (向量类型)**
* **说明**：存储高维浮点数数组（如 768 或 1536 维）。
* **场景**：**RAG (检索增强生成)**、相似度搜索、人脸识别特征值。这是 2026 年数据库最重要的演进。



#### **ARRAY**
* **说明**：允许一列存储多个同类型值。
* **场景**：标签系统（如 `tags: ['AI', 'Tech', 'VFS']`），无需额外建立中间表。

---

### 关键避坑指南：
1.  **金额别用 Float**：永远使用 `DECIMAL` 或将单位转为“分”后存入 `BIGINT`，否则 $$0.1 + 0.2$$可能会变成$$0.30000000000000004$$。
2.  **Schema-less 的诱惑**：虽然 JSON 很方便，但过度使用会导致查询性能下降且失去强类型约束。
3.  **向量检索的索引**：对于 `VECTOR` 类型，必须配合特殊的索引（如 HNSW 或 IVFFlat），否则全表扫描会慢到不可接受。

这份设计已经非常扎实，涵盖了数据发现（Discovery）和基本统计分析（Profiling）的核心字段。对于一个 **Data Agent** 来说，它已经能完成 80% 的任务。

但如果要让 Agent 达到“资深数据工程师”的水平，尤其是在处理**数据治理、性能优化和复杂血缘分析**时，目前的元数据还可以从以下四个维度进行增强：

---

### 1. 治理与安全维度 (Security & Governance)
这是企业级应用中最重要的“护栏”。如果 Agent 不知道哪些数据是敏感的，它可能会在回答中泄露 PII（个人隐私信息）。

| 建议添加字段 | 类型 | 说明 | 适用对象 |
| :--- | :--- | :--- | :--- |
| **`pii_flag`** | bool / str | 标记是否包含敏感信息（如：EMAIL, PHONE, PWD）。 | Column |
| **`storage_size`** | str/int | 磁盘占用大小（如 "1.2 GB"）。有助于 Agent 评估查询成本。 | Table / DB / File |
| **`owner`** | str | 数据负责人或所属部门。 | Table / Directory |
| **`access_control`** | list | 权限简述（只读、脱敏、禁止访问）。 | All |

**示例（Column）**:
```yaml
pii_flag: "SENSITIVE_EMAIL"  # 提醒 Agent 在展示时必须脱敏
storage_size: 1500000        # 1.5MB
```

---

### 2. 物理与工程维度 (Engineering & Performance)
Agent 在写 SQL 或操作大数据时，如果没有物理布局信息，可能会写出“全表扫描”的自杀式查询。

| 建议添加字段 | 类型 | 说明 | 适用对象 |
| :--- | :--- | :--- | :--- |
| **`partition_keys`** | list | 分区键。告诉 Agent 必须在 WHERE 中带上这些字段。 | Table |
| **`is_indexed`** | bool | 是否有索引。决定了过滤查询的速度。 | Column |
| **`encoding` / `format`** | str | 物理存储格式（Parquet, ORC, Avro）。 | Table / File |
| **`compression`** | str | 压缩算法（Snappy, Gzip）。 | File |

**示例（Table）**:
```yaml
partition_keys: ["dt", "region"]  # Agent 会自动生成包含 dt=... 的查询
storage_format: "Parquet"
```

---

### 3. 血缘与生命周期维度 (Lineage & Freshness)
Agent 需要知道数据“新鲜不新鲜”，以及“从哪儿来的”。

| 建议添加字段 | 类型 | 说明 | 适用对象 |
| :--- | :--- | :--- | :--- |
| **`freshness`** | str / datetime | 最后一次数据写入/更新的时间（非元数据修改时间）。 | Table / CSV |
| **`update_frequency`** | str | 更新频率（Hourly, Daily, Real-time）。 | Table |
| **`upstream`** | list | 上游依赖（例如该表是由哪几个原始表合并的）。 | Table / View |
| **`downstream`** | list | 被哪些视图或看板引用。 | Table |

**示例（Table/View）**:
```yaml
freshness: "2026-04-03T10:00:00Z" 
update_frequency: "Daily"
upstream: 
  - "raw_db.users_log"
```

---

### 4. 深度语义与模式维度 (Advanced Semantics)
针对你提到的 JSON 和复杂字段，增强 Agent 的推理直觉。

| 建议添加字段 | 类型 | 说明 | 适用对象 |
| :--- | :--- | :--- | :--- |
| **`value_pattern`** | str | 正则表达式或格式描述（如 "YYYY-MM-DD"）。 | Column |
| **`unit`** | str | 度量单位（如 "USD", "kg", "seconds"）。 | Column |
| **`inferred_schema`** | dict | **针对 JSON 的递归结构摘要**（解决你担心的嵌套问题）。 | JSON / Column |
| **`constraints`** | list | 除了 PK 以外的约束（Check 约束, Unique 约束）。 | Column |

**示例（JSON/Column）**:
```yaml
inferred_schema:  # 递归描述内部结构
  user: { type: "Object", presence: 1.0 }
  user.id: { type: "Integer", presence: 1.0 }
  user.tag: { type: "Array", presence: 0.15 }
unit: "USD"
```



---

### 总结：Agent 的认知增强清单

如果你觉得现在的元数据已经很重了，可以按**“优先级”**添加：

1.  **最高优先级：`PII 标记` 和 `分区键`**。前者关乎安全，后者关乎生存（防止查死数据库）。
2.  **次高优先级：`数据新鲜度 (Freshness)`**。防止 Agent 基于过期数据得出错误结论。
3.  **可选：`数据血缘 (Lineage)`**。这对于回答“这个指标是怎么算出来的”这种高阶问题至关重要。

是的，Grep 工具默认会截断。

  Grep 的截断规则

  ┌─────────────┬──────────────────────┬──────────────────────────────┐
  │    参数     │        默认值        │             说明             │
  ├─────────────┼──────────────────────┼──────────────────────────────┤
  │ head_limit  │ 250                  │ 最多返回 250 行/条结果       │
  ├─────────────┼──────────────────────┼──────────────────────────────┤
  │ output_mode │ "files_with_matches" │ 只返回文件路径（不返回内容） │
  └─────────────┴──────────────────────┴──────────────────────────────┘

  实际场景

  场景 1：默认只返回文件路径（不容易超）
  Grep(pattern="TODO")  # 返回匹配的文件列表，最多250个文件

  场景 2：返回内容时容易截断
  Grep(pattern="TODO", output_mode="content")  # 只显示前250行匹配内容

  场景 3：大量匹配时的提示
  如果截断了，我会看到类似：
  [Showing first 250 matches of 5234 total]

  我的应对策略

  1. 先看文件列表（不截断风险小）
  Grep(pattern="TODO", output_mode="files_with_matches")

  2. 针对特定文件再读内容
  Read(file_path="specific_file.py", offset=100, limit=50)

  3. 用 offset 翻页（如果需要看更多）
  # 第一页
  Grep(pattern="TODO", output_mode="content", head_limit=250, offset=0)

  # 第二页
  Grep(pattern="TODO", output_mode="content", head_limit=250, offset=250)

  4. 缩小范围
  # 只在特定目录
  Grep(pattern="TODO", path="src/components", output_mode="content")

  # 只看特定文件类型
  Grep(pattern="TODO", glob="*.py", output_mode="content")

  5. 先用 count 估算量
  Grep(pattern="TODO", output_mode="count")  # 看总共有多少匹配

  - "搜索 TODO，先看有哪些文件"
