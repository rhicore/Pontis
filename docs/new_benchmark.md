# New Benchmark: 从执行结果正确转向业务正确

## 背景

Text-to-SQL 的最终目标是满足用户的业务目标。我们把该目标的达成称为业务正确。

现有 benchmark 常用执行结果正确性作为可计算指标：执行 predicted SQL 和 golden SQL，然后比较两边结果是否一致。这种指标可执行、可复现，但它不等价于业务正确。通常来说，执行结果正确是更机械、更窄的标准；它可以作为业务正确的一个强信号，但不能完整代表业务正确。

当前希望探索的新评测基准，是把评测单元从“整张执行结果表相等”改成“若干关键业务断言成立”。每个样本先被拆成少量业务子问题，每个子问题对应一个可自动核验的单元格标准答案，再用这些断言评估预测结果是否满足业务目标。

## 现有执行结果评测的错位

### 业务正确但执行结果错误

这类问题中，预测结果满足用户业务目标，但由于和 golden SQL 的结果表不完全一致，被执行结果评测判错。

常见形态：

- 同一个业务问题存在多种等价 SQL 写法，例如日期年份用字符串截取或日期函数提取，过滤含义一致，但执行结果比较因为类型、格式、排序或表达式差异判错。
- 问题要求最高、最低、最多、最少时，业务上返回所有并列对象是合理的；标注 SQL 可能只用 `ORDER BY ... LIMIT 1` 返回其中一个，导致并列超集被判错。
- 百分比、比例、单位或四舍五入口径不同，例如一个答案输出 `0.12`，另一个输出 `12` 表示 12%。业务含义接近，但直接执行结果不相等。
- 预测结果包含题目需要的核心答案，但输出列比 gold 更丰富，例如额外返回名称、解释字段、排序指标或辅助列。业务用户能读懂答案，但表格形状和 gold 不一致。
- 预测 SQL 使用更自然的展示形式，例如把代码值转成人类可读标签、把分开的字段拼成完整名称、把多行结果聚合成列表。业务表达更友好，但和 gold 的原始字段或原始行形状不同。

这类问题是新评测基准最适合解决的部分。关键是不要比较整张结果表，而是抽取能代表业务目标的核心断言，并在比较时支持容差、单位归一、标签等价、并列处理、额外列忽略等机制。

### 执行结果满足标注但业务逻辑明显不合理

这类问题中，golden SQL 自身可能存在标注错误或异常口径。预测 SQL 如果贴合正常业务逻辑，反而会被判错；而满足 gold 的结果不一定满足题面业务目标。

常见形态：

- question 和 evidence 指向最大值，但 gold SQL 实际按升序取第一行，得到的是最小值。执行结果贴合标注，但和题面业务目标相反。
- gold SQL 使用明显异常的布尔条件、字段组合或 join 路径，使结果能通过标注评测，但很难解释为正常业务查询。
- 题目要求实体层面的事实，例如“不含某元素的分子”或“患有某病的患者”，gold 却按底层明细行逐行判断，业务含义被改变。
- evidence 给出一个阈值或条件，gold SQL 使用另一个阈值或条件。模型按 evidence 执行会被判错，但 gold 本身和题面说明冲突。

这类问题不能靠自动业务断言完全修复。如果断言生成器盲从 `gold_sql` 和 `gold_result`，它会把 gold 的错误继续固化为新的断言。更合理的处理是标记为 `annotation_issue` 或 `needs_review`，从自动正确率中单独拆出来审计。

### 自然语言歧义和标注口径含混

Text-to-SQL 本身带有自然语言歧义。很多问题存在多种合理解释，而数据集只能提供一种 gold 口径。这类问题经常和标注错误混在一起。

常见形态：

- 自然语言说 `patients/cards/users/players` 时，可以理解为唯一实体，也可以理解为 join 后的明细记录。BIRD gold 经常保留检查记录、属性记录、legalities 记录、postHistory 记录等明细行。
- 题目说 `id` 时，可能指业务实体 id，也可能指某张事实表或属性表的行 id。不同表里的 id 都能 join，但业务粒度不同。
- 问题要求 top-k 时，可以理解为严格返回 k 行，也可以理解为返回所有并列候选。gold 往往采用 `LIMIT k` 的机械口径。
- 问题要求“列出所有元素、标签、类型、历史记录”时，可以输出多行明细，也可以按实体聚合成一个列表。两种形式业务上都能解释，但执行结果形状不同。
- 百分比问题里，分母可能是全部实体、过滤后的实体、join 后明细行、唯一患者/用户/card，或者某个 evidence 指定集合。自然语言通常不会把分母说得足够精确。
- 标签字段可能保留数据库原始编码，也可能转换成解释性文本。例如 `+/-`、`YES/NO`、状态码、原始 tag 字符串等，业务展示口径和 gold 原样返回口径可能不同。

这类问题应显式进入 `ambiguous` 或 `needs_review` 队列，而不是强行计入同一个二值正确率。

## 新评测基准方案

新方案不是继续放宽执行结果 matcher，而是把评测拆成三层。

### 1. Assertion generation

输入一个样本：

```json
{
  "question": "...",
  "evidence": "...",
  "gold_sql": "...",
  "gold_result": {
    "columns": ["..."],
    "rows": [[...]],
    "row_count": 0,
    "truncated": false
  }
}
```

调用大模型生成少量业务子问题。每个子问题只核验一个关键事实，标准答案是一个单元格或 `row_count`。

当前草稿脚本：

```bash
scripts/new_benchmark/generate_business_assertions.py
```

当前输出结构：

```json
{
  "sample_id": "Q",
  "db_id": "database",
  "business_goal": "用户业务目标摘要",
  "assertions": [
    {
      "id": "A1",
      "subquestion": "业务子问题",
      "expected_cell": "单元格标准答案",
      "gold_result_ref": {
        "row_index_1based": 1,
        "column": "column_name"
      },
      "comparison": "exact",
      "unit_or_scale": null,
      "tolerance": null,
      "source": "result",
      "note": "说明"
    }
  ],
  "needs_review": false,
  "review_reason": null
}
```

设计原则：

- 简单单值题通常生成 1 个断言。
- 复杂报表通常生成 3 到 8 个关键断言。
- 断言数量由模型根据业务重要性选择，不按结果表单元格机械展开。
- 每个 `expected_cell` 来自一个 gold result 单元格或 `row_count`。
- 跨列概念只选择关键组成单元格核验，例如姓名拆成 first name / last name，而不是拼成一个新值。
- 截断结果只用 `row_count` 和可见行关键单元格生成断言；完整列表、全表存在性、distinct 数等放入 `review_reason`。

### 2. Assertion evaluation

对预测 SQL 执行结果进行同样粒度的业务核验，而不是整张表比对。

比较器需要支持：

- `exact`：字符串、整数、日期、原始标签等精确比较。
- `numeric_close`：普通数值比较，支持 tolerance。
- `percentage_close`：百分比或比例比较，支持 0-100 与 0-1 尺度归一。
- `boolean_exact`：布尔断言。

后续还需要考虑：

- 排序无关集合或局部顺序。
- top-k 和并列候选。
- 额外列忽略。
- 标签等价，例如 raw code 与可读标签。
- NULL、空字符串和大小写格式。

### 3. Sample triage

每个样本最终不应只有 correct / wrong 两个状态。建议拆成：

- `auto_gradable`：断言明确，可自动评测。
- `business_correct`：预测结果满足业务断言。
- `business_wrong`：预测结果不满足业务断言。
- `ambiguous`：自然语言存在多个合理解释。
- `annotation_issue`：question/evidence 与 gold SQL/result 存在明显冲突。
- `needs_review`：自动断言生成或自动比较不足以可靠判断。

这样可以把模型能力问题、数据集标注问题、自然语言歧义问题分开统计。

## 单元格抽样作为补充方案

除了让模型主动选择关键业务断言，也可以从 gold execution result 中抽取若干单元格，再要求模型围绕这些单元格生成可核验的子问题。例如从结果表中抽 5 个单元格，生成 5 个对应问题，每个问题的标准答案就是被抽中的单元格。

这个思路适合作为 coverage 补充，而不适合作为唯一评测逻辑。

优点：

- 每个子问题天然有唯一标准答案，比较逻辑简单。
- 可以避免整张结果表 equality 过于苛刻的问题。
- 多行多列结果能覆盖不同列、不同排名、不同分组。
- 实现成本低，便于快速构造一个 table-grounded question generation 基线。
- 能防止模型只生成过于抽象或过于容易的断言。

隐患：

- 随机单元格不一定关键，可能抽到辅助列、重复值、NULL、常量列或业务价值很低的格子。
- 单个单元格通常无法体现核心 SQL 口径，例如百分比分母、排序候选集合、distinct/重复行、join 粒度。
- 围绕单元格反向造题，可能生成和原始 question 业务目标关系很弱的问题。
- 重复值会让评测变弱，例如某列全是同一个标签或同一个计数。
- 截断结果会带来风险，模型可能从预览行推断全表结论。
- 预测结果可能碰巧包含几个抽样单元格，但整体业务目标仍然没有完成。

更稳妥的做法是混合策略：

- 主体由模型根据 question/evidence/gold_result 选择少量关键业务断言。
- 额外加入少量结果表抽样断言，作为 coverage 补充。
- 抽样采用分层策略，优先覆盖排序边界、top-k 首尾行、非重复值、非 NULL、数值列、标签列、与 question/evidence 关键词相关的列。
- 每个抽样单元格需要能解释它和原始业务目标的关系，关系弱的抽样结果进入 review 或丢弃。

因此，推荐的方向不是纯随机抽格子，而是：

```text
关键业务断言 + 分层单元格抽样断言
```

前者保证业务正确性，后者保证结果覆盖度。

## 当前小规模验证

已用 BIRD dev 中几个复杂报表样本做过初步测试，覆盖以下类型：

- 多槽位输出：管理员 first/last name，部分槽位为 NULL。
- 多指标输出：OWNER / DISPONENT 两个计数。
- top-k 多列输出：set name 和 id。
- 重复行明细：postHistory type id 多行重复，NumberOfUsers 在每行重复。
- 多列极值答案：milliseconds、driver name、race name。
- 多行明细列表：molecule_id 与 element 明细。
- 截断大表：只暴露前 20 行预览，但 row_count 显示总行数更大。

调整后观察到：

- 模型能把复杂报表压缩成少量关键断言，而不是逐格展开。
- 重复行问题可以用 row_count、关键行、重复值位置等断言表达。
- 百分比和数值尺度可以进入 `unit_or_scale` 和 `tolerance`。
- 对截断结果，必须把全表结论放进 `review_reason`，否则模型容易从预览行推断全表事实。
- 对跨列概念，prompt 需要强调 `expected_cell` 取自单个单元格或 `row_count`，否则模型会把 first name + last name 拼成新值。

## 能解决什么，不能解决什么

能明显改善：

- 业务正确但执行结果表形状不同。
- 额外输出列导致的错判。
- 百分比尺度、数值容差、单位差异。
- top 并列、排序、重复行等局部口径问题。
- 多行报表中核心业务事实正确，但整体表格不完全一致。

不能自动解决：

- gold SQL 本身违反 question/evidence。
- gold result 固化了明显错误的业务口径。
- 自然语言多解释且多个解释都合理。
- 需要完整结果才能判断但输入只给了截断预览。

这些样本应该进入 review 或 annotation issue，而不是强行计入自动业务正确率。

## 结论

当前 Text-to-SQL 评测的核心问题不是再提出一个更高精度的 SQL 生成方法，而是评测基准本身需要从机械执行结果正确转向业务正确。

新 benchmark 的目标不是简单“放宽”原有结果比对，而是建立：

```text
业务断言正确率 + 歧义/标注问题审计
```

这样才能区分：

- 模型真的没有满足用户业务目标。
- 模型满足了业务目标，但输出形式与 gold 不一致。
- gold SQL 或 evidence 存在标注问题。
- 自然语言问题本身存在多个合理解释。
