这是对于prompt写作实现的人工指示,agent实现必须永远按照这个来,ai禁止修改这个文件!


1. 永远指示该做什么,不要因为之前模型写了什么错误工具调用你就为了这个打补丁而写"不要做什么"等负面规则,你指示负面规则agent反而会混乱,你要做的是使工具调用和prompt符合模型直觉,让他拿来就用,而不是在用之前还要想什么不该用
    - 安全/权限/硬约束类负面规则可以保留，例如只读、删除不可逆、SQL 只读、工具调用上限。
    - 为了纠正某次模型坏调用而新增的补丁式负面规则要删，例如“不要写 project/...”“不要用某个刚犯错的 ref 形式”。
    - 通用任务偏好如果本质是 benchmark 口径，也可以保留，但最好用正向表述；比如 BIRD 的 DISTINCT、输出列、JOIN 粒度这些不是补丁，是数据集风格规则。
2. 不要出现冗余,相同的规则只应该出现一遍,不要把同一条规则写的到处都是,
3. 权责清晰,一处的prompt只介绍一部分模块的内容,尽量减少耦合,你永远要考虑假如一个模块(一个工具,一个系统提示词逻辑)变动了,它对应的prompt变动,你写的到处都是交叉到时候还要全局改
4. 工具的使用指南里面永远只写硬性的使用规则,涉及到具体的字段属性名/建议/工作流/软性的内容放到_tool里面
5. 不要写他妈的架构设计过程，一个agent看到的应该只是它完成任务所需要的最小范围的提示词！尤其不要把你自己的思考，还有和用户讨论过程中的内容泄露给agent，agent不需要乱七八糟的信息！！
6. 你在考虑一个agent 的提示词的时候永远要把它当成一个没有你上下文的独立操作员，你和用户讨论的大部分信息他都没有也不知道，所以你需要有个无知之幕，假定你没有和用户讨论的上下文，一个空白的agent会是怎么操作的。
7. 提示词不要一直打补丁，你应该从更high level的层面审视提示词逻辑，打补丁只会让提示词变得又臭又长，小模型反而难以理解
