# Dev 集测评模式：独立测评与连续测评

## 背景

当前 dev 集测评默认把每一道题当作独立任务处理：

- agent 不借鉴前面已经测过的 dev SQL
- 不把同库前序题目的成功或失败经验写回给后续题

这种设定最接近传统 benchmark 的“静态测评”。

但从 data agent 的真实使用场景看，这并不是唯一合理的设定。真实系统往往会：

- 在同一数据库上连续工作
- 逐步记住局部 schema 规律
- 把前面问题中学到的 join、字段语义、库内习惯复用到后面

因此，dev 测评实际上可以分成两种不同模式。

## 模式一：独立测评

### 定义

每道题都被当作独立任务处理：

- 不读取当前 dev 集前面题目的求解经验
- 不把前面题的局部结论写回当前库知识层
- 不允许后面的题继承前面题的临时记忆

### 它测什么

- 当前库理解能力
- 通用 SQL 生成能力
- 跨库知识迁移能力
- 不依赖测试时在线学习的单次求解能力

### 优点

- 和传统 benchmark 更一致
- 结果更容易和标准 zero-shot / agent baseline 对齐
- 不受题目顺序影响

### 缺点

- 忽略了真实 data agent 会持续积累局部经验的事实
- 对“同库连续使用”的工业场景不够贴近
- 会低估系统的在线适应能力

### 适合的命名

- `Independent Dev Evaluation`
- `Per-Query Independent Evaluation`

如果推理时不使用 train 样例或 train 检索，这一模式也更接近：

- `zero-shot dev evaluation`

但前提是不要把 train few-shot 直接塞进上下文。

## 模式二：连续测评

### 定义

同一个 dev 数据库内部允许跨题积累经验：

- 后面的题可以借鉴前面已经测过的题
- 可把前序题中发现的局部 join、字段映射、库内约定写回临时记忆
- agent 会在同库中“越做越懂这个库”

### 它测什么

- test-time adaptation 能力
- 库内连续使用下的在线学习能力
- 局部经验沉淀能力
- 同库多轮工作下的稳定性

### 优点

- 更贴近工业场景
- 更符合真实 data agent 的工作方式
- 能更真实地体现“局部库理解会不会随着使用改善”

### 缺点

- 不再是传统意义上的独立 benchmark 测评
- 结果受到题目顺序影响
- 容易产生记忆污染
- 不同运行顺序可能得到不同准确率

### 适合的命名

- `Sequential Dev Evaluation`
- `Dev Evaluation with Test-Time Memory`
- `Online Dev Evaluation`

## 两种模式的核心差别

| 维度 | 独立测评 | 连续测评 |
|---|---|---|
| 题目之间是否共享经验 | 否 | 是 |
| 是否允许库内在线学习 | 否 | 是 |
| 是否受题目顺序影响 | 否 | 是 |
| 更贴近传统 benchmark | 是 | 否 |
| 更贴近工业使用 | 否 | 是 |

## 为什么需要把两者区分开

如果不加区分，就容易把两种不同能力混在一起：

1. 单题泛化能力
2. 同库连续使用下的在线适应能力

这两种能力都重要，但不是一回事。

例如：

- 一个系统可能独立测评分数一般，但连续测评提升明显
- 这说明它的基础泛化一般，但 test-time adaptation 很强

反过来：

- 一个系统可能独立测评很高，但连续测评没有进一步提升
- 这说明它单题能力强，但局部经验沉淀能力一般

## 对当前系统的意义

从目前 dev 错误来看，很多错误并不是“完全不会”，而是：

- 同一个库里的局部规律没有被及时复用
- 高风险 join、字段映射、局部约定没有形成可持续记忆

例如：

- `california_schools` 中 `satscores.cds <-> schools.CDSCode`
- `rtype='S'` 的局部语义
- `formula_1` 中部分时间字段的比较口径
- `card_games` 中某些统计是否该 `DISTINCT`

这些规律如果允许在同库内逐步沉淀，后续题理论上是可以获益的。

因此，对当前系统来说，连续测评不是作弊视角，而是一个合理的研究问题：

- 系统能否在不看 train 的情况下，在单个新库上逐步变得更懂这个库？

## 需要明确的风险

连续测评虽然合理，但要注意它改变了实验语义。

一旦允许后续题借鉴前序题经验，就不能再把结果简单表述为：

- `zero-shot dev accuracy`
- `independent dev benchmark accuracy`

更准确的表述应该是：

- `dev accuracy under sequential evaluation`
- `dev accuracy with test-time memory`
- `online adaptation performance on dev`

## 建议的实验汇报方式

建议以后同时保留两套结果：

### 1. 独立测评

用于回答：

- 在不借助 dev 内记忆的前提下，系统本身的泛化能力有多强？

### 2. 连续测评

用于回答：

- 如果允许系统在同库连续工作并积累经验，它能提升多少？

这两套结果一起报，信息量最大，也最容易解释。

## 对连续测评的实现约束建议

如果后续真的要做连续测评，建议至少加上这些约束：

### 1. 记忆只允许在同库内部传播

不要让：

- `california_schools` 的 dev 内记忆泄漏到 `formula_1`
- 一个库的局部经验污染另一个库

### 2. 记忆内容尽量结构化

优先记录：

- 局部 join 规则
- 字段消歧
- 路由知识
- 局部约定

不建议直接记录：

- 原始问题和完整 SQL

否则会把实验变成近似的 dev 内 few-shot 检索。

### 3. 记录题目顺序

连续测评必须把题目顺序作为实验条件的一部分写清楚。

否则结果无法复现，也无法公平比较。

### 4. 最好同时报告首题性能和收敛后性能

这样能区分：

- 初始泛化能力
- 在线适应收益

## 结论

dev 集中的 SQL 不必被系统永远当作“独立同分布、每题失忆”的任务。

但只要允许后续题借鉴前序题经验，测到的就不再是标准的独立 benchmark 能力，而是：

- test-time memory 能力
- 在线适应能力
- 同库连续工作能力

因此，最合适的做法不是二选一，而是把两种模式都明确命名、明确区分、分别汇报。
